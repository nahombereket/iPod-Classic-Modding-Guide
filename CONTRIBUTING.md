# Contributing

This project is a repair guide. Accuracy, scope, and a reader’s ability to stop safely matter more than covering every possible mod quickly.

## Before opening a pull request

1. Check that a procedure is model-specific; do not merge notes from different iPods into one universal guide.
2. Use [the procedure template](docs/templates/procedure.md) for new hands-on guides.
3. Give a direct source or reproducible test record for each compatibility, capacity, runtime, price, and safety claim.
4. Mark community experience as a report, including the model, firmware, adapter revision, storage media, and date.
5. Add photos only if you created them, have permission, or meet the source’s reuse terms. Write useful alt text.

## Required procedure elements

- scope and explicit exclusions;
- difficulty, risk, tools, exact parts, and fitment requirements;
- preparation and safety checks before disassembly;
- numbered actions with observable checkpoints;
- an open-case/pre-close test and final verification;
- direct links to videos or references at the step where they help;
- sources and outstanding validation work.

## Style

Use short, imperative sentences: “Release the latch,” “Inspect the ribbon,” “Stop if the case bows.” Avoid hype, unsupported superlatives, filler, and unqualified claims such as “works with all cards.” Do not publish affiliate links or price claims without clear disclosure and a check date.

## Testing a contribution

At minimum, check relative links, Markdown rendering, spelling of model names, heading order, and `git diff --check`. For hardware work, describe what you actually tested and what you did not.
